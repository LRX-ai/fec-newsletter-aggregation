# Transaction type map

_Generated by `tools/build_transaction_map.py` — do not edit by hand._

How every `TRANSACTION_TP` in `usa.fec_pac_to_pac` is treated. Descriptions are verbatim from [FEC's published code list](https://www.fec.gov/campaign-finance-data/transaction-type-code-descriptions/).

The **send** pipeline attributes a newsletter from the sender's catcode. The **receive** pipeline attributes from the recipient CANDIDATE's congressional committee seats — not from a catcode, because candidates have none.

**"Used by: send + receive" does not mean the money moves both ways.** It means both pipelines consume that transaction type, attributing the same row from opposite ends. A `24E` independent expenditure backing a member of House Agriculture counts as **the paying PAC's industry sent it** in one output and **Agri-Food policy received it** in the other — same dollar, two questions.

Do not union `send_quarterly.csv` and `receive_quarterly.csv`: they are two answers about the same money, not two halves of one total.

Committee-to-committee codes are **send only** — receive needs a candidate, and those rows have none on either end. Candidate-directed codes feed both.

Note that *outflow / inflow* below and *send / receive* are unrelated axes. Outflow and inflow describe **which column holds the payer** inside the OTH file (`CMTE_ID` or `OTHER_ID`); send and receive describe **which pipeline** uses the row.

The `→ send $` / `→ receive $` columns count only what survives to each output, and only the OTH share of send (the rest comes from PAS2). They are far below the raw amounts because most committee-to-committee money involves party and leadership-PAC catcodes, which CRP leaves outside the industry newsletters.

**Classify on the description's verb, not the shape of the code.** `30K`/`31K`/`32K` are *receipts* despite sharing a `K` suffix with `24K` "Contribution **made** to nonaffiliated committee" — they were misfiled as outflows at first, which swapped sender and recipient on 824 rows worth $30.1M.
